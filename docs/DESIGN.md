# GPUC 项目研发设计思路

> 项目：基于 GPU 的服务资源卸载技术探索（GPU-based Transparent Disk I/O Compression）
> 参赛：2026 全国大学生计算机系统大赛 — OS 功能挑战赛道
> 队伍：西安交通大学 404notfound

---

## 1. 问题背景与研究动机

### 1.1 存储压缩的价值

在大数据、日志分析、数据库、编译缓存等业务中，磁盘 I/O 往往是关键瓶颈。存储压缩可以：

- **减少磁盘占用**：全零、重复模式、文本类数据可压缩数倍甚至数十倍；
- **提升有效读带宽**：从磁盘读取的数据量减少，在 I/O 受限场景下可间接提升吞吐；
- **降低存储成本**：对冷数据、归档数据尤为重要。

传统存储压缩多在 CPU 上完成（如 btrfs zstd、ZFS lz4、应用层压缩）。当系统 CPU 成为瓶颈，或需要处理高吞吐实时解压时，将压缩/解压任务卸载到 GPU 这种高并行加速器成为一种可行方向。

### 1.2 现有方案的局限

| 方案 | 优点 | 缺点 |
|---|---|---|
| 文件系统内置压缩（btrfs/zstd、ZFS lz4） | 性能高、对用户透明 | 需要格式化或迁移数据，侵入性强 |
| FUSE 用户态文件系统 | 不修改内核 | 路径切换、额外拷贝带来较高 overhead |
| device-mapper / LVM 压缩层 | 对上层透明 | 需要 root 权限，配置复杂，风险高 |
| 内核模块 / eBPF | 性能潜力大 | 开发周期长，兼容性、稳定性风险高 |
| 应用层手动压缩 | 灵活 | 需要修改业务代码，无法通用 |

因此，我们希望设计一种**非侵入、可透明叠加、对现有应用零修改**的 GPU 压缩卸载方案。

### 1.3 为什么 GPU 适合做解压？

- **高内存带宽**：GPU 显存带宽远高于 CPU 内存带宽，适合数据密集型解压；
- **大规模并行**：每个 128 KB block 可拆分为 32 个独立 4 KB chunk，天然适合 CUDA thread/block 并行；
- **异步流水线**：CUDA Stream 可与 I/O 重叠，隐藏 H2D/D2H 传输延迟；
- **通用算力**：即使没有专用压缩硬件，也可通过 CUDA kernel 实现自定义压缩算法。

## 2. 设计目标

本项目提出 **GPUC（GPU-Compress）**，一个基于 `LD_PRELOAD` 的用户态透明存储压缩层，核心设计目标如下：

| 目标 | 具体含义 |
|---|---|
| **非侵入式** | 不修改操作系统内核、不改造现有文件系统、不改动应用源码 |
| **透明叠加** | 通过 `LD_PRELOAD` 在 ext4/xfs 之上插入压缩层，现有二进制无需重新编译 |
| **离线压缩** | 写路径只写 RAW 数据，后台 Daemon 异步完成压缩，避免阻塞前台写 |
| **GPU 卸载** | 读路径对压缩文件自动调用 GPU 批量并行解压 |
| **GPU 通用算力** | 默认 SGLZ 算法不依赖 NVIDIA nvCOMP 等闭源压缩库，体现 CUDA 通用计算能力 |
| **可插拔后端** | 可选 `GPUC_ALGO=lz4` 启用 NVIDIA nvCOMP LZ4，文本类数据压缩率更优 |
| **可替换后端** | 提供独立 GPU 与 CPU Hook/Daemon；CPU 路径需显式启用 |
| **数据一致性** | CRC32 校验、原子替换、fsync 语义保持正确 |

## 3. 总体方案：LD_PRELOAD + 离线 Daemon

系统由两大核心组件构成：

1. **`libgpuhook.so`**（LD_PRELOAD 拦截层）：
   - 拦截应用的标准 POSIX I/O 调用；
   - 新文件写入时附加 56 B RAW header；
   - 读压缩文件时查 header、读 block entry、批量 GPU/CPU 解压、返回原始数据；
   - 拦截 `mmap/munmap/msync`，使压缩文件可被透明映射；
   - 拦截 `stat` 系列调用，向上层报告逻辑大小，隐藏物理稀疏大小。

2. **`gpu_compress_daemon`**（离线压缩守护进程）：
   - 扫描目录，发现 RAW 文件后批量 GPU 压缩；
   - 生成临时压缩文件，通过 `rename()` 原子替换原文件；
   - 支持一次扫描模式和周期性守护模式；
   - 根据可压缩率决定是否保留压缩结果，避免负压缩。

整体数据流见 `architecture.md`，本文不再赘述。

## 4. 关键设计决策

### 4.1 为什么选用 LD_PRELOAD？

| 候选方案 | 侵入性 | 开发周期 | 兼容性风险 | 性能上限 |
|---|---|---|---|---|
| LD_PRELOAD | 无 | 短 | 低 | 受用户态切换和 PCIe 限制 |
| FUSE | 中 | 中 | 中 | 两次用户态切换、拷贝 overhead 大 |
| device-mapper | 高 | 长 | 高 | 内核态，性能高 |
| 内核模块 / eBPF | 极高 | 极长 | 极高 | 理论上最优 |

选择 LD_PRELOAD 的核心原因是**以最小的部署代价实现透明叠加**：
- 不需要 root 权限即可对特定进程启用；
- 不需要格式化文件系统或迁移数据；
- 不需要重新编译应用；
- 风险可控，出现 Bug 时只需取消 `LD_PRELOAD` 即可恢复。

代价是性能上限低于内核态方案，但通过 batch、流水线、read-ahead 等优化，已能在多数场景接近 Baseline。

### 4.2 为什么 128 KB 分块？

- **对齐 GPU 并行粒度**：128 KB = 32 × 4 KB，每个 chunk 由一个 CUDA block 处理，grid 配置规整；
- **匹配存储系统习惯**：128 KB 是许多 SSD 和文件系统的推荐 I/O 粒度；
- **索引表大小可控**：1 GB 文件仅需 8192 个 block entry（约 192 KB 索引），header 开销可忽略；
- **随机读粒度适中**：过小会增加索引开销，过大会放大小随机读的解压浪费。

### 4.3 为什么“先写后压”？

- **避免写路径阻塞**：实时压缩会显著增加 `write()` 延迟，尤其对不可压缩数据；
- **错峰运行**：Daemon 可在业务低峰期运行，减少资源竞争；
- **选择性压缩**：可根据文件热度、可压缩率决定是否压缩；
- **保持简单语义**：写路径只追加 header，不修改数据布局，降低正确性风险。

代价是“写后立即读”无法命中 COMPRESSED 状态，为此引入低可压缩率 fallback 和 RAW 直接透传来缓解。

### 4.4 为什么默认 SGLZ，同时支持 LZ4？

- **SGLZ（Simple GPU LZ）**：
  - 本队自主实现的 CUDA 压缩算法，不依赖闭源 nvCOMP；
  - 体现 GPU 通用算力，符合大赛对“独立完成度”的考察；
  - 对高重复数据压缩率极好（全零 3.2%），对不可压缩数据可快速 fallback。

- **nvCOMP LZ4**：
  - 对本机 Linux headers 文本语料的 allocated ratio 显著优于 SGLZ
    （81.8% → 38.1%）；
  - 长期 worker、持久 buffer 和 32-block read-ahead 后 warm read 为
    178.6 MiB/s，约为旧正式值 81.0 MiB/s 的 2.21 倍；
  - 仍远低于普通文件 warm Baseline；当前价值是 CPU offload 与空间，不是文件
    读取加速；
  - 作为可选后端，通过 `GPUC_ALGO=lz4` 启用，保持向后兼容。

双后端共存使系统保留自研核心算法，同时可在空间优先场景选择成熟库；后端选择
必须根据实测空间/吞吐权衡，不能假设 LZ4 在当前实现中更快。

### 4.5 为什么用紧凑格式 + slot 布局两级表示？

- **磁盘紧凑格式**：每个 chunk 只写实际压缩长度，避免固定 slot 造成的空间浪费；
- **GPU slot 布局**：每个 chunk 固定 4352 B slot，便于 kernel 中按索引直接寻址，无需前缀和；
- **紧凑格式解压 kernel**：在 GPU 内通过 `chunk_offsets` 索引表将紧凑数据直接解析到 slot，避免 CPU 侧 `memcpy`。

### 4.6 为什么引入文件级 fallback？

实验发现，当数据可压缩率约 25% 时，GPU 解压读带宽（224 MB/s）甚至低于全随机数据的 RAW fallback（296 MB/s）。原因是：
- 低可压缩数据仍需执行 GPU 解压；
- 节省的 I/O 不足以覆盖解压计算 overhead。

因此 Daemon 在整文件压缩完成后计算整体压缩率，若高于阈值（默认 85%）则丢弃压缩结果，保持 RAW 状态。

## 5. 高可用与兼容性设计

### 5.1 CPU Fallback

- **Lazy Init**：`hook_init` 不立即初始化 CUDA，第一次 I/O 时才触发；
- **显式 CPU 路径**：无 GPU 环境使用 `libcpuhook.so` 与 `cpu_compress_daemon`；
- **负载检测实验开关**：只有设置 `GPUC_ENABLE_NVIDIA_SMI_FALLBACK=1` 才低频调用
  `nvidia-smi`；默认关闭，避免在读热路径创建子进程。稳定的自动切换仍是后续工作。

### 5.2 数据库文件白名单

SQLite、LevelDB 等数据库文件在 offset 0 处具有严格 magic/header，56 B RAW header 会破坏格式。系统维护白名单（`.db`、`.wal`、`.log`、`.ldb`、`.sst`、`CURRENT`、`MANIFEST-*`），命中后直接透传，不附加 GPUC header。

### 5.3 数据一致性

- **CRC32 校验**：每 block 存储 CRC32，Hook 解压后验证；
- **原子替换**：Daemon 使用 `rename()` 原子替换，避免读到半完成文件；
- **fsync 语义**：Hook 拦截 `fsync` 并保持正确语义；
- **崩溃一致性**：kill -9 后文件仍可正常 open/read。

## 6. 创新点总结

1. **非侵入式 GPU 存储压缩卸载**：在国内系统类赛事中较少见的、通过 `LD_PRELOAD` 实现透明 GPU 压缩卸载的完整方案。
2. **自主 SGLZ CUDA 压缩算法**：不依赖 nvCOMP，体现 GPU 通用算力，对高重复数据达到 3.2% 压缩率。
3. **多级性能优化体系**：batch decompress、device memory pool、io_uring、
   read-ahead、pinned memory 和 CUDA streams；各项增益需由修正后的消融实验复核。
4. **mmap 正确性路径**：返回前同步填充完整逻辑内容；真正页级按需解压尚未实现。
5. **可插拔压缩后端**：SGLZ 与 nvCOMP LZ4 共存，兼顾自主知识产权与真实数据压缩率。
6. **文件级压缩率 fallback**：低压缩收益时保留 RAW；GPU/CPU 运行时自动切换仍有限制。
7. **完整工程化与测试体系**：17+ 自动化测试脚本覆盖性能、稳定性、容错、真实 workload、能耗等多维度。

## 7. 与同类方案的定位差异

| 维度 | btrfs zstd | 应用层压缩 | GPUC（本方案） |
|---|---|---|---|
| 侵入性 | 高（需特定文件系统） | 高（需改应用） | 无 |
| 部署难度 | 中 | 高 | 低（LD_PRELOAD） |
| 性能上限 | 高（内核态） | 取决于实现 | 中（用户态 + GPU） |
| 压缩后端 | 固定 | 灵活 | 可插拔 SGLZ / LZ4 |
| GPU 卸载 | 否 | 可选 | 是 |
| 适用场景 | 新建系统 | 特定应用 | 现有系统透明叠加 |

GPUC 的核心价值不在于单点性能超越内核态方案，而在于**以极低的部署成本，为现有系统提供透明、可卸载、可降级的存储压缩能力**。
