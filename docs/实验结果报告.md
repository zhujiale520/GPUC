# GPUC 实验结果报告

> 更新日期：2026-08-09  
> 本报告仅呈现最能支撑项目结论的核心实验。完整原始结果保存在
> [`results/final/`](../results/final/)，不在正文逐项展开。

## 1. 实验目标与结论

GPUC 使用 `LD_PRELOAD` 透明接入应用 I/O，由后台 Daemon 将 RAW 文件离线压缩，
读取 COMPRESSED 文件时调用 CPU 或 GPU 后端解压。实验主要回答三个问题：

1. GPU 解压能否降低主机 CPU 竞争，并把资源释放转化为业务收益；
2. 透明存储路径在 fio、Vdbench 和真实 SQLite 业务中是否正确、稳定；
3. GPU 路径对主机 DRAM 带宽的影响是什么。

核心结论如下：

| 证据 | 主要结果 |
|---|---|
| RTX 4090 同吞吐卸载 | 约 4 GiB/s 下，GPU 相对 CPU 多保留 13.05% 业务吞吐，解压路径 CPU 时间降低 96.4% |
| RTX 4090 SQLite | GPU 相对 CPU QPS 提高 11.21%，p99 降低 81.66%，解压进程 CPU 时间降低 88.0% |
| fio 与 Vdbench | fio 多线程 60/60、Vdbench 50/50 样本完成，错误数为 0，逻辑 SHA-256 一致 |
| 长期稳定性 | RTX 4090 连续读取 1 小时，fio error=0，运行前后 SHA-256 一致 |
| 故障恢复 | ENOSPC、Daemon SIGKILL、残留临时文件重启、GPU 不可见回退和 `/dev/full` 共 5/5 通过 |
| V100 DRAM 同吞吐对照 | 约 4 GiB/s 下，GPU 路径总主机 DRAM 带宽比 CPU 路径低 47.75% |

实验说明 GPU 卸载的主要价值是释放主 CPU 和降低特定场景下的主机 DRAM 压力，
而不是让所有压缩读取都超过普通文件路径。

## 2. 实验平台与方法

### 2.1 主要平台

| 项目 | RTX 4090 平台 | V100 平台 |
|---|---|---|
| GPU | NVIDIA GeForce RTX 4090 24 GB，sm_89 | Tesla V100-SXM2-32GB，sm_70 |
| CPU | Intel Xeon Gold 6238 | x86_64 服务器平台 |
| 操作系统 | Linux 6.8.0 | Linux 5.15.0 |
| fio | 3.28 | 3.16 |
| 主要用途 | 核心卸载、SQLite、fio、Vdbench、一小时稳定性 | 同吞吐 PCM DRAM 对照 |

V100 与 RTX 4090 来自不同整机，跨平台数字不解释为只替换 GPU 后的严格 A/B。
报告的正向结论优先使用同一台机器、相同输入和相同吞吐下的 CPU/GPU 对照。

### 2.2 统一实验口径

- Baseline、CPU 和 GPU 场景使用相同逻辑工作量；
- 核心资源实验将 CPU/GPU 解压目标限制为约 4096 MiB/s；
- 正式短实验通常重复 5 次，保存逐轮数据、均值和 95% 置信区间；
- fio 与 Vdbench 使用内容一致但物理独立的测试文件；
- 每组正确性实验检查错误码、文件状态和逻辑 SHA-256；
- `pidstat`、`sar`、`nvidia-smi` 和 Intel PCM 保存原始采样，不使用截图代替数据。

## 3. 核心实验一：GPU 解压卸载

该实验让 4 个 CPU 业务线程与解压任务并行运行。CPU 和 GPU 路径处理同一批
CPU 生成的 LZ4 block，并将逻辑解压吞吐限制在约 4096 MiB/s，避免因两条路径
处理量不同而产生不公平比较。

RTX 4090 五轮结果：

| 场景 | 业务吞吐 ops/s | 解压吞吐 MiB/s | 解压相关 CPU 时间 | 最大 RSS KiB |
|---|---:|---:|---:|---:|
| Baseline | 1,231,899,210 | 0 | 0 | 140,800 |
| CPU LZ4 | 1,083,823,885 | 4,093.81 | 4.7906 s | 271,181 |
| GPU LZ4 | 1,225,301,183 | 4,094.61 | 0.1727 s | 364,848 |

GPU 相对 CPU 路径的业务吞吐提高 **13.05%**。CPU LZ4 的提交/解压 CPU 时间为
4.7906 秒，GPU 路径提交线程与 Worker 合计为 0.1727 秒，降低约 **96.4%**。
这说明长期 GPU Worker 能把高吞吐解压从主 CPU 移出，使并行业务更接近无解压
Baseline。

GPU 路径最大 RSS 高于 CPU，因此该实验不说明主机内存容量下降。对应原始数据：
[`resource_rtx4090_gpu1_final_20260806T145935Z`](../results/final/resource_rtx4090_gpu1_final_20260806T145935Z/summary.csv)。

## 4. 核心实验二：SQLite 并行业务

SQLite 实验使用 100000 行、每行 512 B payload 的数据库，4 个业务进程执行
只读 indexed range aggregate；同时运行约 4096 MiB/s 的 CPU 或 GPU 解压任务。
每个场景运行 5 轮。

| 场景 | QPS | 相对 Baseline | p99 | 解压进程 CPU 时间 |
|---|---:|---:|---:|---:|
| 无解压 | 13,467.85 | 100.00% | 349.71 μs | 0 |
| CPU LZ4 | 11,486.95 | 85.29% | 2,640.29 μs | 2.9120 s |
| GPU LZ4 | 12,775.12 | 94.86% | 484.23 μs | 0.3494 s |

GPU 相对 CPU 路径 QPS 提高 **11.21%**，p99 降低 **81.66%**，解压进程 CPU
时间降低 **88.0%**。GPU 场景仍比无解压 Baseline 低 5.14%，说明卸载减少了
CPU 解压带来的干扰，但没有消除全部系统开销。

对应原始数据：
[`sqlite_range_offload_rtx4090_gpu1_20260807T153922Z`](../results/final/sqlite_range_offload_rtx4090_gpu1_20260807T153922Z/summary.csv)。

## 5. 核心实验三：fio 与 Vdbench

### 5.1 fio 多线程正确性与退出稳定性

fio 使用 64 MiB 非零可压缩 pattern，覆盖 SGLZ/LZ4、4/16/128 KiB、1/4 线程，
每个组合重复 5 次，共 60 个样本。

| 算法 | 块大小 | 1 线程 MiB/s | 4 线程 MiB/s | 错误/超时 |
|---|---:|---:|---:|---:|
| SGLZ | 4 KiB | 80.35 | 303.62 | 0/0 |
| SGLZ | 128 KiB | 145.95 | 527.60 | 0/0 |
| LZ4 | 4 KiB | 281.10 | 1,104.55 | 0/0 |
| LZ4 | 128 KiB | 290.71 | 1,141.71 | 0/0 |

60/60 样本的 fio error 均为 0，进程按时退出，读取内容与输入 SHA-256 一致。
这组实验主要验证两种压缩格式在多线程存储工具中的正确性与生命周期稳定性。

对应原始数据：
[`fio_threads_rtx4090_gpu1_final_20260806T151148Z`](../results/final/fio_threads_rtx4090_gpu1_final_20260806T151148Z/summary.csv)。

### 5.2 Vdbench 端到端 I/O

Vdbench 5.04.07 使用 256 MiB 文件、4 线程、2 秒预热、10 秒计时，每个场景重复
5 次。读实验比较 Baseline、Hook RAW、SGLZ 和 LZ4；70:30 混合读写只比较可写的
Baseline 与 Hook RAW。

| 路径 | 128 KiB 顺序读 MiB/s | 4 KiB 随机读 MiB/s |
|---|---:|---:|
| Baseline | 20,796.79 | 2,387.20 |
| Hook RAW | 19,250.20 | 2,446.74 |
| SGLZ | 83.32 | 2.70 |
| LZ4 | 137.50 | 9.59 |

顺序读、随机读和混合读写共 50/50 个样本完成，文件状态正确，逻辑 SHA-256
一致。压缩路径仍慢于普通文件，尤其是 4 KiB 随机读取；该结果作为当前 128 KiB
压缩粒度和用户态逐请求开销的适用边界保留。

对应原始数据：
[`vdbench_rtx4090_gpu1_final_20260806T151148Z`](../results/final/vdbench_rtx4090_gpu1_final_20260806T151148Z/summary.csv)。

## 6. 核心实验四：长期稳定性与故障恢复

### 6.1 RTX 4090 一小时持续读取

测试使用 512 MiB COMPRESSED 文件、128 KiB 块、4 个 fio job，连续运行 3600 秒。

| 指标 | 结果 |
|---|---:|
| 平均带宽 | 473.79 MiB/s |
| 平均 IOPS | 3,790.34 |
| p99 | 5,734.4 μs |
| 带宽变异系数 | 10.44% |
| fio error | 0 |
| 运行前后 SHA-256 | 一致 |

该实验用于证明持续读取不会报错或损坏数据，不作为 GPU 绝对速度超过 CPU 的证据。
对应原始数据：
[`stability_1h_rtx4090_gpu1_final_20260806T151148Z`](../results/final/stability_1h_rtx4090_gpu1_final_20260806T151148Z/summary.csv)。

### 6.2 故障恢复

| 故障场景 | 验证结果 |
|---|---|
| Daemon 压缩中注入 ENOSPC | 保留原 RAW 和 SHA，清理临时文件 |
| 原子替换前 SIGKILL | 原 RAW 未改变且仍可读取 |
| 残留临时文件后重启 | 重启后生成有效 COMPRESSED 文件 |
| GPU 不可见 | CPU fallback 回读 SHA 一致 |
| 写入 `/dev/full` | 内核错误正确向上传播 |

五项测试全部通过。对应原始数据：
[`fault_recovery_rtx4090_gpu1_gap_20260807T143659Z`](../results/final/fault_recovery_rtx4090_gpu1_gap_20260807T143659Z/summary.csv)。

## 7. 核心实验五：主机 DRAM 带宽

Intel PCM 采集全系统 IMC 带宽。主结论使用 V100 机器上的 512 MiB 轮转工作集，
CPU/GPU 都达到约 4093 MiB/s，每个场景重复 5 次并只统计完整稳态区间。

| 场景 | DRAM Read MB/s | DRAM Write MB/s | DRAM Total MB/s |
|---|---:|---:|---:|
| Baseline | 23.80 | 20.53 | 44.33 |
| CPU LZ4 | 4,416.34 | 4,329.12 | 8,745.46 |
| GPU LZ4 | 86.40 | 4,483.11 | 4,569.51 |

相同逻辑吞吐下，GPU 总 DRAM 带宽比 CPU 低 **47.75%**。GPU 路径降低了主机
内存读取压力，但 D2H 结果仍需写回主机内存，所以 GPU 写带宽没有下降。

RTX 4090 的 PCM 采样已经完成，但 PCM 包裹运行时 CPU/GPU 实际吞吐分别约为
3404.1/1314.1 MiB/s，不满足同吞吐前提。因此该组只保留为平台饱和现象，不用于
计算 GPU 相对 CPU 的 DRAM 降幅。

V100 同吞吐原始数据：
[`pcm_dram_512m_v100_20260730`](../results/final/pcm_dram_512m_v100_20260730/summary.csv)。

## 8. 国产平台阶段性验证（2026-08-15）

在 openEuler 22.03、2 路 64 核 Kunpeng-920/AArch64 上，CPU-only 目标已原生构建；
POSIX、损坏头拒绝、2000 个格式 fuzz 和扫描 workload smoke 全部通过。16 MiB、
128 blocks 端到端样本经 CPU Daemon 压缩后透明读取，内容模式和 SHA-256 均一致。

天数智芯 PCIe 设备 `1e3e:0002` 已绑定 `iluvatar 4.4.0`，`ixsmi` 识别为
Iluvatar MR-V100 32 GiB。CoreX Clang 18.1.8 以 `ivcore11` 架构完成项目构建；SGLZ
单元测试中重复数据压缩至 8.7%、全零数据至 2.2%、随机数据正确回退。16 MiB、
128 blocks 经 GPU Daemon 压缩后由 GPU Hook 透明读取，内容与 SHA-256 均一致。
项目原有 CoreX 模式单元与集成测试套件亦全部通过，包括混合块、INLINE、共享 fd
并发 `pread` 和 procfs passthrough。

第二阶段将 32 个 128 KiB 输入打包到持久 Pinned staging buffer，以单次批量 H2D
替代逐块提交；输出在同一 stream 上异步 D2H 后统一同步。通过
`GPUC_SGLZ_COALESCE=0/1` 对同一二进制做 A/B：压缩吞吐由 845.929 提升至
985.727 MiB/s（1.165x），解压由 688.415 提升至 718.622 MiB/s（1.044x）。累计
16 GiB、131072 blocks 的压缩/解压 round-trip 全部一致；另一个 1 GiB 文件经 GPU
Daemon 压缩后连续透明读取 3 次，SHA-256 均为
`49bc20df15e412a64472421e13fe86ff1c5165e18b2afccf160d4dc19fe68a14`。
记录见
[`domestic_poc_kunpeng920_corex_20260815`](../results/final/domestic_poc_kunpeng920_corex_20260815/README.md)。
性能与压力原始摘要见

## 9. 适用范围

- GPUC 当前价值集中在高压缩率、高吞吐并且 CPU 资源紧张的读取场景；
- 压缩文件的 fio/Vdbench 绝对吞吐仍低于普通文件，不宣称 GPU 路径全面更快；
- 4 KiB 随机读受 128 KiB 压缩块和用户态调度固定开销影响，不是优势场景；
- 低压缩率数据会缩小 CPU、DRAM 和空间收益，无法压缩时回退 RAW；
- 当前实现覆盖动态链接应用和只读 COMPRESSED 对象，尚未实现 DM/ZFS 生产后端；
- CoreX 首轮数据搬运优化已实测；真实 NVMe、多进程并发、功耗/能效和赛题指定 RTX
  型号仍需要对应环境实测。

## 10. 总结

GPUC 已形成“功能—性能—稳定性—资源”证据闭环：透明读写和两种压缩格式可用；
RTX 4090 同吞吐实验表明 GPU 能明显降低解压 CPU 时间并保护并行业务；SQLite
验证了真实业务收益；fio、Vdbench、一小时稳定性和故障注入证明了工程正确性；
V100 PCM 同吞吐数据补充了主机 DRAM 压力变化。

消融、Batch、H2D/D2H、mmap、cold-cache、压缩率梯度、Btrfs、公开数据集和完整
I/O 矩阵等附加实验仍保存在 `results/final/`，用于追问和审计，不再占用主报告篇幅。
