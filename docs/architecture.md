# GPU Compress - 架构设计文档

## 1. 设计目标

| 目标 | 说明 |
|------|------|
| **非侵入式** | 不修改内核、不改造文件系统、不改应用代码 |
| **透明叠加** | 在现有文件系统（ext4/xfs）之上插入压缩层 |
| **离线压缩** | 写时不压缩，后台周期性扫描压缩，避免影响前台性能 |
| **GPU 通用算力** | 不依赖专用压缩引擎（如 nvCOMP），体现 CUDA 通用计算能力 |
| **CPU 对比基准** | 提供相同算法的纯 CPU 实现，用于量化 GPU offload 收益 |

## 2. 系统架构

```
┌─────────────────────────────────────────────────────────────┐
│  用户态应用 (fio, cp, dd, 数据库, 业务程序...)               │
├─────────────────────────────────────────────────────────────┤
│  ① LD_PRELOAD 拦截层 (libgpuhook.so)                        │
│     ├─ open()  → 新文件写入 RAW header，已压缩文件读 header   │
│     ├─ write() → 正常写入，不压缩                             │
│     ├─ read()  → RAW 直接透传；COMPRESSED → GPU/CPU 解压      │
│     ├─ lseek() → 逻辑偏移 ↔ 物理偏移转换                     │
│     └─ close() → 清理 fd 元数据                               │
├─────────────────────────────────────────────────────────────┤
│  ② 离线压缩 Daemon                                           │
│     ├─ gpu_compress_daemon: 128K 分块 → GPU batch 压缩        │
│     ├─ cpu_compress_daemon: 128K 分块 → CPU 串行压缩          │
│     └─ 稀疏文件写回，rename 原子替换                          │
├─────────────────────────────────────────────────────────────┤
│  ③ 底层文件系统 (ext4 / xfs)                                 │
└─────────────────────────────────────────────────────────────┘
```

## 3. 数据流

### 3.1 写路径

```
应用 write()
    │
    ▼
LD_PRELOAD hook 拦截
    │
    ├── 新文件？→ 写入 file_header (state=RAW)
    │
    └── 正常 CPU 写入数据（不压缩）
            │
            ▼
        落盘到 ext4/xfs
```

**设计原则**：写路径不压缩，保证前台写性能不受影响。

### 3.2 离线压缩路径

```
后台 Daemon 扫描
    │
    ▼
发现 RAW 文件 (header.state == 0)
    │
    ▼
读取文件数据
    │
    ▼
按 128KB 切分为独立块
    │
    ▼
GPU batch 压缩（一次处理 32 个 block）
    │
    ▼
写回磁盘（稀疏文件对齐，保持逻辑 128K 块边界）
    │
    ▼
更新 header.state = COMPRESSED
    │
    ▼
rename() 原子替换原文件
```

**关键优化**：
- **Batch 处理**：一次性分配 device 内存，启动一个 kernel 处理 32×32=1024 个 chunks
- **稀疏对齐**：压缩后逻辑上仍然占 128KB，物理空间用空洞优化
- **原子替换**：temp file + rename() 保证文件始终可用

### 3.3 读路径

```
应用 read()
    │
    ▼
LD_PRELOAD hook 拦截
    │
    ├── 读取 file_header
    │       │
    │       ├── RAW (state=0)        → 直接 real_read() 返回
    │       │
    │       └── COMPRESSED (state=1)
    │               │
    │               ▼
    │           根据块索引找到对应 128K 块
    │               │
    │               ▼
    │           读紧凑格式 → 转换为 slot 布局
    │               │
    │               ▼
    │           GPU/CPU 解压该块
    │               │
    │               ▼
    │           拷贝到用户 buf 返回
    │
    ▼
应用拿到原始数据（无感知）
```

## 4. 文件格式 (GPUC)

```
┌──────────────────────────────────────────────────────────────┐
│  struct gpuc_header (64 bytes)                               │
│  ├── magic (4B)     = 0x47505543 "GPUC"                     │
│  ├── version (4B)   = 1                                      │
│  ├── orig_size (8B) 原始逻辑大小                              │
│  ├── block_size (4B)= 128KB                                  │
│  ├── num_blocks (4B) 总块数                                   │
│  ├── state (1B)     = RAW(0) / COMPRESSED(1) / BUSY(2)      │
│  ├── comp_algo (1B) = SGLZ(1)                                │
│  └── header_size (8B) 头+索引表总大小                         │
├──────────────────────────────────────────────────────────────┤
│  block_index_table[]                                         │
│  ├── block_entry[0] { orig_len, comp_len, offset }           │
│  ├── block_entry[1] { orig_len, comp_len, offset }           │
│  └── ...                                                     │
├──────────────────────────────────────────────────────────────┤
│  压缩数据（紧凑格式）                                          │
│  ├── block_0: chunk_0_len(2B) + data + chunk_1_len(2B) + ... │
│  ├── block_1: ...                                            │
│  └── ...                                                     │
│  （稀疏文件空洞保持 128KB 逻辑对齐）                            │
└──────────────────────────────────────────────────────────────┘
```

## 5. SGLZ 压缩算法

### 5.1 分块策略

| 层级 | 大小 | 处理方式 |
|------|------|----------|
| File | 任意 | 按 128KB 切分 |
| Block | 128KB | 32 个独立 chunk |
| Chunk | 4KB | 1 个 CUDA block / CPU 线程处理 |

### 5.2 Chunk 级 LZ77

- **Hash**：3-byte 滚动哈希，256 槽位
- **滑动窗口**：2048 字节（限制 offset 以节省编码空间）
- **最小匹配**：4 字节
- **最大匹配**：255 字节（1 字节编码）
- **标记**：
  - `0x00 + len(2B) + data` = 字面量 run
  - `0x01 + off(2B) + len(2B)` = 回拷引用
  - `0xFFFF` = 未压缩 chunk（直接存储原始 4KB）

### 5.3 布局格式

**Slot 布局（GPU 内部使用）**：
- 32 个固定 slot，每个 4352 字节（4096 + 256）
- 前 2 字节为 comp_len，后续为压缩数据
- 便于 GPU kernel 直接寻址，无需前缀和

**紧凑布局（磁盘存储）**：
- 每个 chunk 的实际长度顺序存放
- 节省空间，读入后需展开为 slot 布局再解压

## 6. 关键技术决策

### 6.1 为什么用 LD_PRELOAD？

| 方案 | 侵入性 | 开发周期 | 风险 | 选择 |
|------|--------|----------|------|------|
| LD_PRELOAD | 无 | 短 | 低 | ✅ |
| FUSE 文件系统 | 中 | 中 | 中 | — |
| device-mapper | 高 | 长 | 高 | — |
| 内核模块 | 极高 | 极长 | 极高 | — |

### 6.2 为什么 128KB 块？

- 对齐 GPU 处理粒度（warp = 32 threads）
- 32 × 4KB = 128KB，正好一个 CUDA block grid
- 匹配存储系统页缓存块大小（常见 4KB/128KB）
- 块索引表大小可控（1GB 文件仅需 8192 个条目 ≈ 192KB）

### 6.3 为什么先写后压？

- 避免压缩影响前台写延迟
- 后台可以错峰运行
- 允许根据数据热度选择性压缩

### 6.4 GPU Batch 优化的必要性

| 处理方式 | 64MB 可压缩数据耗时 | 吞吐 |
|----------|---------------------|------|
| 逐块 cudaMalloc/Memcpy/Free | 0.326s | 196 MB/s |
| **Batch 一次处理 512 块** | **0.035s** | **1844 MB/s** |
| 纯 CPU 串行 | 0.054s | 1181 MB/s |

> 结论：如果没有 batch，GPU 比 CPU 慢 6 倍；batch 优化后获得 1.56x 加速。
