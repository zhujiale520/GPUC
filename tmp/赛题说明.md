## 3. 赛题背景

高性能服务器在处理大量业务时，CPU 资源消耗很高。以全闪存存储服务器为例，
随着 NVMe 磁盘性能迅速提升，仅处理 I/O 本身就会消耗大量 CPU 资源。

如果还需要在服务器上运行其他业务，例如：

- 在存储服务之上运行数据库；
- 在数据库之上运行应用或中间件；
- 同时运行其他计算密集型服务；

主 CPU 的资源会变得更加紧张，不同业务之间还可能因为 CPU 竞争而相互影响性能。

本赛题希望探索通过 GPU Offload 承担部分计算密集型任务，从而降低主 CPU 的资源
消耗，为其他业务释放计算资源。

## 4. 赛题任务

### 4.1 块设备层压缩

通过 Device Mapper（DM）在 block 层实现压缩。

主要优点：

- 位于块设备层；
- 上层可以支持多种文件系统；
- 不依赖特定文件系统的压缩能力。

### 4.2 文件系统层压缩

通过 Btrfs、ZFS 等文件系统实现压缩。

主要优点：

- 文件系统能够感知数据内容；
- 有可能实现更好的压缩效率。

主要限制：

- 方案被锁定在特定文件系统；
- 这些文件系统的绝对性能可能不如 XFS、ext4 等文件系统。

### 4.3 GPU Offload 性能评估

性能指标可以参考公开的相关测试，建立基准后进行实测，分析 GPU Offload 带来的
性能变化。

建议对比以下内容：

- 纯 CPU 实现的性能、CPU 开销和 DRAM 开销；
- GPU Offload 实现的性能、CPU 开销和 DRAM 开销；
- 不同 CPU 架构之间的性能，例如 x86 与 AArch64；
- GPU Offload 是否能够减少主 CPU 的资源消耗；
- GPU Offload 是否能够改善其他并行业务的性能。

### 4.4 测试与分析工具

性能测试工具：

- fio；
- vdbench。

资源分析工具：

- top；
- htop；
- perf；
- stat；
- sar。

测试时应综合分析 I/O 性能、CPU 使用率、内存与 DRAM 开销等指标。

## 5. 赛题特征

GPU Offload 可以作为国产 CPU 在计算密集型任务方面的能力补充，尤其适用于
华为鲲鹏等 AArch64 平台。

赛题强调的不只是利用特定 GPU 的专用压缩引擎，也包括利用 GPU 通用算力完成
压缩与解压任务，以获得更广泛的硬件适配性。

## 8. 评审要点

### 8.1 创新性

NVIDIA 新一代 GPU 提供了压缩相关能力和 nvCOMP 库，但赛题更强调使用 GPU 通用
算力处理压缩、解压等任务。

创新性评价重点包括：

- 是否深入理解 GPU 的架构特点；
- 是否针对 GPU 特点进行了有效性能优化；
- 是否具有更广泛的适配性；
- 是否避免仅依赖最新一代 GPU；
- 是否具备不锁定单一 GPU 供应商的扩展思路。

### 8.2 完整度

项目应满足以下要求：

- 系统能够实际运行；
- 具备完整的性能测试报告；
- 测试用例覆盖相对完整；
- 文档描述清晰；
- 其他开发者能够根据文档完成部署；
- 其他开发者能够完成二次开发与集成。

### 8.3 Demo 质量

Demo 重点考察：

- 稳定性；
- 性能；
- 核心功能是否可以可靠复现。

## 9. 对参赛项目的核心要求概括

参赛项目需要围绕“将存储服务中的计算密集型任务卸载到 GPU”这一目标，至少回答
以下问题：

1. 系统是否能够稳定运行并保持数据正确性；
2. GPU Offload 是否改善了压缩、解压或 I/O 性能；
3. GPU Offload 是否确实减少了主 CPU 和 DRAM 的资源消耗；
4. 被释放的 CPU 资源是否能够提高数据库、应用或中间件等并行业务的性能；
5. GPU 方案相较纯 CPU 方案的性能、资源和适用场景分别是什么；
6. 系统是否具有清晰的部署、测试、二次开发和集成文档；
7. 方案是否具备跨 GPU、跨 CPU 架构和跨存储栈扩展的潜力。
