# GPUC 鲲鹏 920 + 天数智芯 CoreX 部署指南

## 1. 当前适配结论

国产平台采用“两段式验收”：先证明鲲鹏 920/AArch64 上的 Hook、文件格式、CPU
回退和端到端数据正确性，再启用天数智芯 CoreX 的 CUDA 兼容 SGLZ 后端。CoreX
构建不依赖 NVIDIA 专属 nvCOMP；LZ4 文件仍可由 CPU `liblz4` 解码，但国产 GPU
可行性验证使用项目自研 SGLZ。

2026-08-15 在当前机器上的实测状态：

| 项目 | 状态 | 证据/说明 |
|---|---|---|
| CPU | PASS | 2 路、64 核 Kunpeng-920，AArch64，openEuler 22.03 LTS-SP1 |
| AArch64 编译 | PASS | `libcpuhook.so`、CPU Daemon 和测试程序均原生构建成功 |
| CPU smoke | PASS | POSIX、损坏头拒绝、2000 个格式 fuzz、扫描 workload 全通过 |
| CPU 端到端 | PASS | 16 MiB、128 blocks，压缩后透明读取与期望 SHA-256 一致 |
| GPU PCIe/驱动 | PASS | `1e3e:0002`，Iluvatar MR-V100 32 GiB，驱动/CoreX 4.4.0 |
| GPU 编译 | PASS | CoreX Clang 18.1.8，`-x ivcore --offload-arch=ivcore11` |
| GPU kernel | PASS | 最小 kernel 与 SGLZ 压缩/解压单元测试通过 |
| GPU 端到端 | PASS | 16 MiB、128 blocks，GPU Daemon 与 GPU Hook 内容/SHA 一致 |
| 数据搬运优化 | PASS | Pinned staging、合并 H2D/D2H；压缩 1.165x、解压 1.044x |
| 扩大压力 | PASS | 累计 16 GiB/131072 blocks round-trip；1 GiB 文件连续 3 次 SHA 一致 |

因此，鲲鹏 920/AArch64 与天数智芯 CoreX GPU 的功能闭环以及第一轮数据搬运优化
均已验证。该结果证明可行并量化当前优化收益，但不代表已经完成 NVMe、并发和整机
能效调优。

## 3. CoreX 编译器与运行环境

CoreX 4.4.0 的实际 CUDA 编译入口是自带 Clang，而安装目录里的 `nvcc` 仅为版本
兼容脚本。MR-V100 在本机对应 `ivcore11`：

```bash
tmp_dir="$(mktemp -d)"
printf '%s\n' '__global__ void k(void) {}' \
  'int main(void) { k<<<1,1>>>(); return 0; }' > "$tmp_dir/probe.cu"
/usr/local/corex-4.4.0/bin/clang++ -x ivcore \
  --cuda-path=/usr/local/corex-4.4.0 --offload-arch=ivcore11 \
  -c "$tmp_dir/probe.cu" -o "$tmp_dir/probe.o"
test -s "$tmp_dir/probe.o"
rm -rf "$tmp_dir"
```

CoreX 安装目录不同时显式传入：

```bash
make corex COREX_HOME=/opt/corex COREX_GPU_ARCH=ivcore11
```

Codex 默认 Bubblewrap 沙箱用隔离的 `/dev`，普通工具调用可能看不到
`/dev/iluvatar0` 和 `/dev/itrctl`，但这不代表宿主机没有 GPU。GPU 实跑应在宿主机
Shell、正确映射设备的容器，或获批的 Codex 沙箱外命令中执行。

## 4. CoreX 构建与验收

```bash
export COREX_HOME=/usr/local/corex-4.4.0
export PATH="$COREX_HOME/bin:$PATH"
export LD_LIBRARY_PATH="$COREX_HOME/lib64${LD_LIBRARY_PATH:+:$LD_LIBRARY_PATH}"

# 只构建自研 SGLZ GPU 后端，不链接 NVIDIA nvCOMP
make corex COREX_HOME="$COREX_HOME" COREX_GPU_ARCH=ivcore11

# GPU kernel 压缩/解压一致性
./bin/test_compress

# 完整国产平台验收并保存证据
bash scripts/deploy_domestic_poc.sh --require-gpu

# 性能 A/B、累计大规模 round-trip 和大文件端到端压力
bash tests/corex_performance_stress.sh
```

性能脚本默认执行 3 GiB A/B 工作量、累计 64 GiB round-trip，以及 1 GiB 文件三次
透明读取；可用 `GPUC_PERF_MIB`、`GPUC_PERF_ITERATIONS`、`GPUC_STRESS_MIB`、
`GPUC_STRESS_ITERATIONS`、`GPUC_E2E_MIB` 和 `GPUC_E2E_READS` 调整。结果保存在
`results/local/corex_perf_<UTC>/`。

`GPUC_SGLZ_COALESCE=0` 保留旧的小 DMA/逐次同步路径作为 A/B 基线；默认值 `1`
启用持久 Pinned staging、批量 H2D 和同 stream 异步 D2H 后单次同步。2026-08-15
同机实测如下：

| 路径 | 优化前 | 优化后 | 提升 |
|---|---:|---:|---:|
| SGLZ 压缩 | 845.929 MiB/s | 985.727 MiB/s | 1.165x |
| SGLZ 解压 | 688.415 MiB/s | 718.622 MiB/s | 1.044x |

这是 32-block batch、可压缩合成数据的 GPU 算法/传输吞吐，不应替代真实 NVMe、
fio 或业务吞吐结果。

## 5. 平台差异与边界

- AArch64 没有传统 `unlink` syscall，Hook 已使用 `unlinkat` 兼容实现。
- CoreX `ivcore11` 上 SGLZ 不再依赖 CUDA `atomicAdd` 汇总长度，而是每个线程写独立
  chunk 长度并由 Host 归并；这同时保留 NVIDIA 路径的数据格式兼容性。
- 当前机器 `/tmp` 是 tmpfs，不能承载原测试的 `O_DIRECT` 场景；验证脚本默认改用
  项目所在 ext4，也可通过 `GPUC_TEST_ROOT=/data/ext4` 指定。
- CoreX 模式不构建 nvCOMP LZ4 性能工具；`GPUC_ALGO=lz4` 不是本轮国产 GPU
  验收路径。先用默认 SGLZ 证明可行，后续再评估国产 LZ4 GPU 库或自研 LZ4 kernel。
- `fio` 当前未安装；第二阶段已完成算法/传输和大文件正确性压力，真实 NVMe fio、
  多进程并发及整机能效仍需安装依赖并在目标存储介质上复跑。
