# CPU/GPU LZ4 解压吞吐与压缩率敏感性

正式实验使用 128 MiB 轮转工作集、128 个 128 KiB block/batch、4 个业务线程，
解压提交线程和 GPU worker 均绑定 core 0，与业务线程产生同核竞争。目标吞吐为
1024/2048/4096 MiB/s；确定性输入中可压缩页占 0%/50%/100%，对应实际 CPU LZ4
存储比约 100.0008%/50.3259%/0.4936%。每组运行 5 秒、五轮，场景与输入顺序轮换。

命令：

```bash
GPUC_RESULT_DIR="$PWD/results/local/offload_sensitivity_v100_20260731" \
GPUC_RUNTIME=5 GPUC_REPEATS=5 GPUC_WORKSET_MIB=128 \
GPUC_BATCH_BLOCKS=128 GPUC_BUSINESS_WORKERS=4 \
GPUC_DECOMP_CPU=0 GPUC_WORKER_CPU=0 \
GPUC_TARGETS_MIB_S='1024 2048 4096' \
GPUC_COMPRESSIBLE_PCTS='0 50 100' \
bash tests/offload_sensitivity.sh
```

无解压 baseline 业务吞吐为 1,773,926,662 ops/s。下表只将 CPU/GPU 都达到至少
99% 目标吞吐的组作为严格固定吞吐比较；“解压 host core”由提交线程与 GPU worker
的 CPU time 除以墙钟时间得到，不包含四个业务线程。

| 目标 MiB/s | 可压缩页 | 实际存储比 | CPU 业务保留 | GPU 业务保留 | GPU-CPU | CPU 解压 host core | GPU 解压 host core | GPU host 降幅 |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 1024 | 0% | 100.0008% | 93.34% | 93.47% | +0.13 pp | 0.246 | 0.117 | 52.37% |
| 1024 | 50% | 50.3259% | 95.49% | 95.97% | +0.48 pp | 0.176 | 0.164 | 7.00% |
| 1024 | 100% | 0.4936% | 96.32% | 97.09% | +0.77 pp | 0.148 | 0.117 | 20.98% |
| 2048 | 0% | 100.0008% | 87.16% | 87.27% | +0.10 pp | 0.459 | 0.205 | 55.43% |
| 2048 | 50% | 50.3259% | 91.46% | 92.75% | +1.29 pp | 0.335 | 0.286 | 14.72% |
| 2048 | 100% | 0.4936% | 93.00% | 95.34% | +2.34 pp | 0.280 | 0.192 | 31.27% |
| 4096 | 100% | 0.4936% | 87.77% | 91.27% | +3.50 pp | 0.487 | 0.353 | 27.50% |

逐轮配对的 GPU-CPU 业务吞吐差在 1024 MiB/s、0% 输入为 +0.132±0.630 pp，
以及 2048 MiB/s、0% 输入为 +0.104±0.148 pp，均不能证明业务受益。随着吞吐和
可压缩率提高，差异增大；4096 MiB/s、100% 输入为 +3.503±0.084 pp。

4096 MiB/s 的其余两组没有达到公平目标，必须作为饱和结果单列：

| 可压缩页 | CPU 实际 MiB/s | GPU 实际 MiB/s | CPU 目标达成 | GPU 目标达成 |
|---:|---:|---:|---:|---:|
| 0% | 2909.50 | 2983.18 | 71.03% | 72.83% |
| 50% | 3829.90 | 3108.85 | 93.50% | 75.90% |

因此，GPU 解压减少 host CPU 是可重复的，但“为并行业务带来可见收益”依赖吞吐、
压缩率和是否已经接近 CPU 竞争瓶颈。此前单一 4 GiB/s、高可压缩 16 MiB 工作集的
结论不能外推为所有输入；本矩阵将适用边界收窄为可审计的条件结论。PCM 仍只有
4096 MiB/s、高可压缩输入的正式结果，尚未覆盖本矩阵全部组。
