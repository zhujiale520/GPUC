## 1. 总体判断

GPUC 已经实现了一个可运行、可测试的用户态 GPU 存储压缩原型，并完成了较系统的
文件语义、异常格式、并发替换和性能复测。项目目前能够可靠证明：

- GPU 压缩文件能够生成并透明回读，数据一致性通过；
- SGLZ 和 nvCOMP LZ4 两种 GPU 后端可运行；
- read-ahead、batch 和 pinned memory 中前两项各有约 11% 的实测贡献；
- SGLZ 在 1 到 16 个读取线程间有约 2.03 倍扩展；
- LZ4 在 Linux headers 文本样例上将物理占用降低到原始文件的约 38.1%；
- 不可压缩数据能够回退为 RAW，避免无意义压缩。

经过本轮 P0 修复，项目已经在一个明确、可复核的边界内回答了赛题背景：

> CPU/GPU 都固定约 4096 MiB/s 时，长期 GPU worker 的额外主机 CPU 成本约
> 0.403 core，CPU LZ4 为 0.566 core，降低约 28.8%；与业务争用同一核心时，
> GPU/CPU 分别保留 97.17%/89.85% 的业务吞吐。SQLite range aggregate 中，
> GPU 相对 CPU 路径 QPS 高约 7.3%、p99 低约 50.5%。

这证明“GPU offload 能减少固定吞吐压缩任务的主机 CPU 消耗并减轻业务干扰”。
LZ4 请求感知预读进一步消除了 4 KiB 请求触发 4 MiB 读取/解压的内部放大：
严格 fio A/B 中4 KiB随机读吞吐提高4.19–4.90倍、p99降约90%；进一步的小请求
CPU分流把同fixture Vdbench从GPU-only 2.076提高到12.239 MB/s。但压缩文件读取
仍远慢于普通文件Baseline，且混合结果不能称为GPU加速。
512 MiB 稳态 PCM 显示同为约
4094 MiB/s 解压时，GPU/CPU 总 DRAM 带宽约为 4569.51/8745.46 MB/s，GPU
降低约 47.75%；但 GPU D2H 写带宽仍约 4.48 GB/s，最大 RSS 高约 8.94%。
因此可以主张降低该流式工作负载的总 DRAM bandwidth，不能主张节省 DRAM 容量、
消除写回或提高所有存储读取性能。

对照赛题后，当前最重要的剩余判断是：

1. **核心背景问题已在限定实验中回答**：固定吞吐下主机 CPU 成本下降，SQLite
   并行业务受益，总 DRAM bandwidth 下降；
2. **赛题任务层级尚未完全命中**：实现位于用户态 `LD_PRELOAD`，不是 DM block
   层或 Btrfs/ZFS 文件系统层，且 COMPRESSED/INLINE 是只读归档对象；
3. **硬件覆盖仍缺失**：没有鲲鹏 920、赛题指定 RTX 3060/4060/5060、正式 NVMe；
4. **压缩侧结论已经补齐但为负**：同一 LZ4 输入五轮中，真正 batch 相对旧
   serial 至少快 18.34 倍；同为 1024 MiB/s 时 GPU/CPU 主机成本为
   0.365/0.276 core；PCM 总 DRAM 为 1809.39/1396.85 MB/s，GPU 高 29.53%，
   压缩侧不能主张 CPU、DRAM bandwidth 或 RSS 卸载；
5. **工程与真实 workload 证据已补强，性能外推仍有缺口**：全新路径
   CPU/GPU build/test/docs 全部 PASS；CPU/业务与PCM吞吐/压缩率敏感性已完成；
   Btrfs也已补真实log/ELF corpus和文件页缓存失效。剩余外推缺口主要是真实
   corpus资源矩阵、独占NVMe和外部硬件。

| P2-4 | 没有长期稳定性和故障恢复数据 | **已解决·仍有限定**：五项确定性故障 PASS；RTX 4090 一小时 error=0、SHA 一致 | 真实 GPU reset/断电仍需隔离环境 | 一小时持续读已完成；不外推到掉电和GPU reset |
| P2-5 | 缺代码覆盖率 | **已解决**：gcov + CI 门槛 | Hook 41.38%、CPU daemon 62.15%、CPU SGLZ 85.52%、CPU LZ4 70.83% | Hook 行覆盖率不得低于 35% |
| P2-6 | GPU 供应商锁定 | **按用户安排暂缓**：依赖 CUDA/nvCOMP | 后续评估 HIP/SYCL/供应商无关接口 | 当前仍未解决，不包装为跨供应商 |
| P2-7 | mmap、O_DIRECT、应用 io_uring 等能力边界分散 | **已解决**：独立支持矩阵并同步 README/设计/实现/实验/复现 | `docs/SUPPORT_MATRIX.md` 为统一口径 | 验收通过 |

## 4. 现有实验还需要重点体现什么

后续实验报告应围绕赛题背景组织，而不是只按实现模块罗列数据。

### 4.1 必须作为主线呈现

1. **CPU 是否真的被释放**
   - 比较无解压、CPU 解压、GPU 解压三种场景；
   - 同时展示解压吞吐、业务吞吐、CPU user/sys、cycles、context switches；
   - 新结果应展示固定吞吐与核心亲和性，旧的负结果只作为优化前历史。

2. **DRAM 是否真的节省**
   - 比较 CPU/GPU 路径的 RSS、峰值内存、DRAM 带宽和 cache miss；
   - 区分“GPU 显存消耗”和“主机 DRAM 消耗”；
   - 当前 PCM 证明总带宽下降约 47.75%，但 GPU RSS 略高且 D2H 写回仍约
     4.48 GB/s；只能主张该稳态流式负载的总 bandwidth 下降，不能宣称 DRAM
     容量节省或消除写回。

3. **真实业务是否受益**
   - 数据库或中间件业务应报告 QPS 和尾延迟；
   - 业务必须与压缩/解压任务真实并行；
   - 合成 CPU 循环只能作为敏感性分析，不能代替真实业务。

4. **真实存储路径是否受益**
   - 有效 O_DIRECT 已完成；真实 NVMe、不同队列深度仍需外部设备权限；
   - 分开报告顺序/随机、带宽/IOPS、平均/尾延迟；
   - page cache 数据只能说明内存路径扩展性。

5. **不同硬件是否可迁移**
   - V100 证明了“不依赖最新 GPU”，这是可保留的亮点；
   - 仍需要 RTX 指定平台和鲲鹏/AArch64 数据回答赛题平台要求。

6. **压缩侧是否也完成公平卸载**
   - 已完成同一 LZ4 输入五轮吞吐、压缩率、主机 CPU、RSS 和 GPU power；
   - 真 batch 修复有效，但 GPU 同吞吐 host CPU 高 32%，必须展示负结论；
   - PCM 显示 GPU 总 DRAM 高 29.53%，进一步证明不能把解压侧收益外推到压缩侧。

7. **实现层级如何对应赛题**
   - 明确当前是用户态机制探索原型，不是已经完成的 DM/Btrfs/ZFS 方案；
   - 给出向 block/fs 层迁移时的队列、回写、崩溃一致性和 metadata 接口设计；
   - 只读归档模型是当前工程选择，不应描述为通用在线可写压缩文件系统。

### 4.2 可以作为已有亮点呈现

- 正确性与防御性测试覆盖较完整；
- daemon 原子替换和元数据保留；
- SGLZ/LZ4 双后端与不可压缩数据 RAW 回退；
- 1 到 16 线程约 2.03 倍扩展；
- read-ahead 和 batch 各约 11% 的消融贡献；
- batch=4 的工程选择有实验证据；
- LZ4 文本样例约 38.1% 的物理空间占用；
- 对无效 O_DIRECT、旧 jobs=32、错误 mmap 数据主动撤回，实验可信度较高。

### 4.3 不应包装成正向成果

- GPU 在任何吞吐、硬件和业务下都必然释放 CPU；
- 压缩文件读取快于 Baseline；
- 存在正向读取次数 break-even；
- 把 SATA/ext4 的有效 O_DIRECT 数字包装成 NVMe 成绩；
- mmap 每次只解压一个 4 KiB 页，或完整扫描成本已经消失；
- 对任意应用完全透明；
- 已达到生产级；
- 旧 jobs=32 99.8%、mmap 231 ms、LZ4 581 MiB/s 等作废数据。

## 5. 当前仍需处理的问题与建议顺序

### 5.1 现有 V100 可继续补的数据

1. **PCM代表组已完成**：CPU/业务95样本与PCM45样本已经收窄压缩率/吞吐边界；
   若时间允许，只在真实corpus复核1–2个CPU/DRAM代表点；
2. **Btrfs真实数据与文件级失效已完成**：dpkg status/Bash ELF下Btrfs/GPUC
   空间占用36.36%/54.61%，GPUC读取仍落后；该模式不等于刷新设备缓存，真实
   介质测试归入独占NVMe任务；
3. **只读端到端应用已验收为负结果**：SQLite 已直接读取 GPUC 压缩对象且结果
   正确，但细粒度点查性能很差；下一步应优化架构或补更符合批量卸载的大块
   Parquet/备份顺序扫描，而不是重复 SQLite 点查；
4. **压缩侧先优化再回归**：峰值/压缩率梯度已经完成且为负；应先优化 pipeline、
   拷贝和 batch，之后再用同一脚本复测，不重复现状实验；
5. **实际 1 小时稳定性**：现有正式结果只有 10 分钟，不得将脚本默认值
   写成已执行时长。

> 压缩读仍慢于 Baseline 是已验证的负结论。它需要代码/架构优化后重测，
> 不是简单增加重复数就能解决的数据问题。

### 5.2 需要安全存储目标或外部仪器

1. 确认 `nvme0n1` 的分区、文件系统和数据归属后，在明确可写目标复跑
   fio/Vdbench direct I/O；未经确认不得格式化或写裸盘；
2. 使用 RAPL、IPMI 或外部功率计补 CPU package/整机 J/GiB；
3. 精确 `LLC-load-misses` 只在支持相应 PMU 事件的内核/硬件上补测。

### 5.3 需要外部硬件或长期实现

1. 鲲鹏 920/AArch64；
2. 至少一款赛题指定 RTX 3060/4060/5060；3050/4090 只补跨代趋势；
3. ZFS/DM 真正后端实现与性能数据；
4. AMD/Intel GPU 后端仍暂缓，必须继续标为未解决。

### 5.4 已解决、无需原样重复

- 长期 GPU worker、持久资源、D2H 合并和请求感知 LZ4 预读；
- 同吞吐 CPU/GPU 解压、SQLite 并行业务、PCM/perf 资源实验；
- fio、Vdbench、公开 Gutenberg、O_DIRECT 软件路径；
- CPU/GPU 压缩侧 PCM、Btrfs zstd 安全 loop 空间与暖缓存基线；
- 共享 fd、fio 退出卡死、POSIX 语义、mmap、故障恢复、长稳和覆盖率。

上述“已解决”指现有口径的原始数据与正确性已验收，不代表这些结论
可外推到 NVMe、鲲鹏、RTX 或所有数据集。详细数据缺口见 `FINAL_TODO.md`
的 E1–E12。

当前项目最终定位已经可以确定为：

> **面向存储压缩任务的用户态 GPU 服务资源卸载原型。它在固定 LZ4 解压吞吐下
> 降低主机 CPU 和总 DRAM bandwidth，并改善并行业务；尚不是 DM/文件系统层、
> 在线可写或跨供应商的生产级实现。**
